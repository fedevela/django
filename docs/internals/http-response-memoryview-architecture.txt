Issue #59 Memoryview normalization in HttpResponse (Architecture artifact)
=====================================================================

Status: Architecture-ready for implementation (stable boundaries defined, traceability preserved).
Requirements: MEMVIEW-001, MEMVIEW-002, MEMVIEW-003, MEMVIEW-004, MEMVIEW-005

Requirement-to-architecture map
------------------------------
- MEMVIEW-001 -> [django/http/response.py: HttpResponse.__init__]
  - Owns constructor ingress of payload and raw-memoryview normalization contract.
- MEMVIEW-002 -> [django/http/response.py: HttpResponse.__init__ + HttpResponse.content.setter]
  - Owns handling of bytes-backed memoryview including empty payload as constructor input.
  - Ownership is intentionally constructor-only for this issue.
- MEMVIEW-003 -> [django/http/response.py: HttpResponse.make_bytes, HttpResponse.__init__, HttpResponse.content]
  - Owns baseline `str` and `bytes` semantics during ingress and repeated reads.
  - `make_bytes` must preserve existing byte identity for `bytes` and preserve charset-driven encoding for `str`.
  - Constructor must not route `str` or `bytes` through memoryview-specific conversion branches.
  - Getter returns concrete `bytes` output on every access, independent of constructor type.
- MEMVIEW-004 -> [django/http/response.py: HttpResponse.content getter]
  - Owns repeated read behavior contract for normalized memoryview-origin content.
- MEMVIEW-005 -> [django/http/response.py: HttpResponse.__init__, HttpResponse.content getter]
  - Owns constructor-to-content invariant that legacy memoryview stringified payload (`<memory at ...>`) is never surfaced.
  - Verification pressure is split across:
    - `tests/responses/test_memoryview_traceability.py` for explicit contract-focused regression.
    - `tests/httpwrappers/tests.py` for canonical HttpResponse suite regression coverage.

File/module placement decisions
------------------------------
- `django/http/response.py` (existing module)
  - Remains the execution locus for both constructor-time payload acceptance
    and public read path behavior.
- `tests/responses/test_memoryview_traceability.py` (existing test artifact)
  - Remains the verification seam; behavior checks are now required to be implemented
    against public `HttpResponse(...)` and `.content`.
- `tests/httpwrappers/tests.py` (existing test artifact)
  - Remains the canonical suite seam for production-facing regression assertions around constructor memoryview handling.

Ownership and boundaries
-----------------------
- Boundary A: External input boundary (constructor API)
  - Owner: `HttpResponse.__init__`.
  - Responsibility: accept `content` parameter and collapse memoryview objects into a
    stable, byte-normalized internal representation before state entry.
- Boundary B: Internal state boundary
  - Owner: `HttpResponse.content` storage (`self._container`) and setter.
  - Responsibility: hold normalized segments as bytes-like storage units used by read/append semantics.
- Boundary C: Read/contract boundary
  - Owner: `HttpResponse.content` getter.
  - Responsibility: present stable `bytes` on every access by assembling container state
    deterministically.
- Boundary D: Baseline constructor semantics boundary
  - Owner: `HttpResponse.make_bytes` + `HttpResponse.__init__`.
  - Responsibility: keep `str` and `bytes` inputs on the legacy conversion path
    (`str.encode(self.charset)` then `bytes(...)`, `bytes(value)`) and prevent
    memoryview-only normalization from being applied to these baseline types.
- Boundary E: Legacy assignment path boundary (out of scope of this issue)
  - Owner: `HttpResponse.content` setter path and `write()`.
  - Responsibility: unchanged behavior for runtime assignments and streaming-like appends.
- Boundary F: Legacy-output rejection boundary (`MEMVIEW-005`)
  - Owners: `HttpResponse.__init__`, `HttpResponse.content` getter, and regression tests.
  - Responsibility: enforce that constructor-origin memoryview payloads can only be observed as concrete payload bytes, never as `<memory at` string forms.

Interface / contract artifacts
-----------------------------
- Constructor normalization contract (`MEMVIEW-ARCH-INIT`):
  - Input: `content` may be `memoryview`.
  - Output: bytes payload for internal container when input is memoryview, including `memoryview(b"")`.
  - Determinism rule: normalized value is a new immutable `bytes` object.
- Baseline input contract (`MEMVIEW-ARCH-BASE`):
  - Input: `content` is `str` or `bytes`.
  - `str` output: `bytes(value.encode(self.charset))` so existing charset behavior is preserved.
  - `bytes` output: `bytes(value)` so byte semantics are preserved.
  - Contract says this path is not rewritten to a memoryview conversion branch.
- Read contract (`MEMVIEW-ARCH-READ`):
  - Input: internal `self._container`.
  - Output: `bytes` value from deterministic join.
  - Stability rule: repeated getter calls return equal `bytes` objects for constructor-normalized memoryviews.
- Failure contract:
  - Conversion/type failures remain constructor-initialization failures (no deferred recovery in getter).
- Legacy-rejection contract (`MEMVIEW-ARCH-005`):
  - Input: constructor receives `memoryview(b"My Content")`.
  - Processing: constructor normalization and content materialization must not re-render as memoryview `repr`.
  - Assertions required on `.content`:
    - `not payload.startswith(b"<memory at ")`
    - `payload != b"<memory at 0x"`
    - `payload == b"My Content"`

Dependency-direction notes
-------------------------
- `HttpResponse.__init__` depends on constructor normalization branch before delegating payload to setter.
- `HttpResponse.content` getter depends only on `self._container` state and does not re-interpret original constructor input.
  - `HttpResponse.content` setter remains downstream from request-level `__init__` behavior and must not
  absorb constructor-specific branch logic.
- `HttpResponse.make_bytes` depends on `self.charset` for all non-binary values.
- Charset and content-type defaults therefore remain in `HttpResponseBase` contract; this prevents any
  MEMVIEW-003 refactor from bypassing header/encoding source-of-truth.

Integration-seam skeletons
--------------------------
- Constructor-only normalization seam:
  - Location: constructor comment/pseudocode block in `django/http/response.py`.
  - Purpose: one-way transformation from external `memoryview` -> internal bytes.
- Deterministic read seam:
  - Location: `HttpResponse.content` getter.
  - Purpose: return stable assembled bytes for each access without state mutation.
- Baseline semantics seam:
  - Location: `HttpResponse.make_bytes` and constructor comments in `django/http/response.py`.
  - Purpose: codify that `str` and `bytes` always follow legacy conversion semantics and that no memoryview-specific
    branch runs for these inbound baseline types.
- Regression seam:
  - Location:
    - `tests/responses/test_memoryview_traceability.py::HttpResponseMemoryviewTraceabilityTests.test_memview_005_constructor_memoryview_rejects_legacy_memory_repr`
    - `tests/httpwrappers/tests.py::HttpResponseTests.test_memoryview_constructor_rejects_legacy_payload_rendering`
  - Purpose: assert deterministic negative rejection of legacy representation while preserving direct byte equality.
- Verification seam:
  - Location: `tests/responses/test_memoryview_traceability.py`.
  - Purpose: ensure each requirement ID has explicit test coverage name and explicit legacy-output rejection checks for `MEMVIEW-005`.
